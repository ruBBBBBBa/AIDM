Arquitectura Propuesta para Iberdrola: Optimización del Alumbrado Público en Bizkaia

(Enfoque en escalabilidad, cumplimiento normativo y alineación con el stack existente)

1. Contexto y Objetivos

Iberdrola busca transformar la gestión del alumbrado público en Bizkaia mediante una solución de datos y AI que aborde tres pilares críticos:

  1. Predicción proactiva de fallos para evitar caídas de tensión (KPI: 80% de detección temprana).
  2. Optimización energética en tiempo real y con proyecciones (KPI: 15% de reducción de consumo).
  3. Integración de datos heterogéneos (MQTT, SCADA, GIS, SAP, AEMET) en una arquitectura escalable, regulada (NIS2, ISO 27001) y alineada con su madurez corporativa (Azure Data Lake, Databricks, Power BI).

Restricciones clave:

  • Presupuesto ajustado: 600K€ primer año (priorizar piloto con 50K dispositivos).
  • Equipo limitado: 6 personas con habilidades en Python, Spark y SQL (evitar soluciones complejas).
  • Plazo: Piloto en 6 meses; despliegue completo en 18 meses.
  • Cumplimiento: NIS2 (sector energético) y ENS (servicio público).

2. Arquitectura Propuesta

La solución sigue un enfoque orientado a eventos + lakehouse, con capas claras para escalabilidad y cumplimiento. Se prioriza la reutilización de infraestructura existente (Azure Data Lake, Databricks, Power BI) y se evitan duplicidades.

2.1. Capa de Ingestión (Tiempo Real y Batch)

  • Fuentes de datos:

    • MQTT (2000 concentradores): Lecturas cada 15 minutos (20 GB/día). Se usa Azure Event Hubs por su capacidad para manejar alto volumen de eventos con baja latencia (<1 minuto para alertas críticas). Justificación: Event Hubs es nativo para MQTT, escalable y compatible con el stack Azure. Alternativa descartada: IoT Hub (más costoso y complejo para este caso).
    • SCADA: Datos históricos y en tiempo real. Se integra mediante Azure Data Factory con conectores nativos para APIs REST/SOAP. Justificación: SCADA es mantenido por proveedores externos; ADF evita desarrollo custom.
    • SAP S/4HANA: Datos de inventario y facturación. Se extraen mediante OData Services + ADF con CDC (Change Data Capture) para actualizaciones en tiempo real. Justificación: SAP ya está en Azure; ADF reduce la carga de desarrollo.
    • GIS (ArcGIS o Azure Maps): Para geolocalización. Se usa Azure Maps (más económico y compatible con Power BI). Justificación: El cliente no tiene preferencia definida; Azure Maps cumple con los requisitos de visualización geográfica.
    • AEMET (meteorológicos): Datos abiertos estructurados. Se consumen mediante Azure Logic Apps para orquestar llamadas a su API y almacenar en el lakehouse. Justificación: Solución serverless y de bajo coste para datos externos.

  • Almacenamiento intermedio:

    • Azure Data Lake Storage Gen2 (ADLS): Zona bruta para datos sin procesar (MQTT, SCADA, AEMET). Justificación: Ya lo usan en el corporativo; soporta datos semiestructurados y es compatible con Delta Lake para ML.
    • Delta Lake: Capa de curación para datos procesados (features para modelos). Justificación: Permite versionado, ACID y auditoría, esencial para cumplimiento normativo.

2.2. Capa de Procesamiento

  • Procesamiento en tiempo real:

    • Databricks (Spark Structured Streaming): Para limpieza, enriquecimiento (ej: geolocalización con GIS) y agregación de datos MQTT/SCADA. Justificación: El equipo conoce Spark/Python; Databricks es su herramienta corporativa para ETL y ML.
    • Flujo:
      1. Datos MQTT → Event Hubs → Databricks (ventanas de 5 minutos para detección de anomalías).
      2. Datos SCADA/SAP → ADF → ADLS (zona bruta) → Databricks (procesamiento por lotes).

  • Procesamiento por lotes:

    • Azure Synapse Analytics: Para consultas SQL sobre datos históricos (ej: análisis de tendencias de consumo). Justificación: Más económico que Databricks para cargas analíticas no intensivas y compatible con Power BI.
    • Feature Engineering:
      • Creación de variables para modelos (ej: "temperatura media por hora" usando AEMET, "histórico de fallos por luminaria").
      • Almacenamiento en Delta Lake para trazabilidad y reutilización.

2.3. Capa de AI/ML

  • Modelos de predicción:

    1. Predicción de fallos:
      • Tipo: Clasificación binaria (fallo/sin fallo).
      • Modelo: XGBoost o LightGBM (interpretables y rápidos para datos tabulares).
      • Entrenamiento: Datos históricos de SCADA + telemetría MQTT.
      • Despliegue: API en Azure Machine Learning para integración con alertas.
      • Justificación: Modelos simples y eficientes para el piloto; escalables a otros activos IoT.
    2. Optimización energética:
      • Tipo: Regresión (consumo vs. variables como hora, temperatura, estado de la luminaria).
      • Modelo: Prophet (series temporales) o LSTM (si hay patrones complejos).
      • Entrenamiento: Datos de consumo (SCADA) + meteorológicos (AEMET).
      • Justificación: Prophet es robusto para datos con estacionalidad (ej: consumo nocturno).
    3. Detección de anomalías:
      • Tipo: No supervisado (ej: Isolation Forest o Azure Anomaly Detector).
      • Uso: Identificar patrones atípicos en telemetría (ej: voltaje inestable).
      • Justificación: Reduce la carga de etiquetado manual para datos sin fallos registrados.

  • Orquestación de ML:

    • Azure ML Pipelines: Para retraining automático (ej: semanal) y despliegue de modelos como APIs.
    • MLflow (en Databricks): Para experimentación y seguimiento de versiones.
    • Justificación: Azure ML gestiona el ciclo de vida del modelo en producción; MLflow es conocido por el equipo.

2.4. Capa de Consumo y Visualización

  • Herramientas:
    • Power BI Premium: Para dashboards operativos (alertas en tiempo real) y reportes ejecutivos.
      • Ejemplos de visualizaciones:
        • Mapa de calor de fallos predichos (Azure Maps).
        • Gráficos de ahorro energético por barrio.
        • Alertas en tiempo real integradas con Azure Logic Apps (ej: notificaciones a equipos de mantenimiento).
      • Justificación: Ya lo usan en el corporativo; conectores nativos para Azure ML y Azure Maps.
    • Azure Logic Apps: Para automatizar flujos de trabajo (ej: enviar alertas a SAP o sistemas internos).
      • Justificación: Serverless y de bajo coste para integraciones puntuales.

2.5. Capa de Gobernanza y Cumplimiento

  • Azure Purview:
    • Catalogación automática de datos en ADLS (etiquetado de PII, aunque sea mínimo).
    • Clasificación de datos sensibles (ej: SCADA).
    • Justificación: Cumplimiento obligatorio con NIS2 e ISO 27001.
  • Azure Policy:
    • Reglas para cifrado, acceso por roles (ej: solo lectura para modelos) y cumplimiento de ENS.
    • Justificación: Automatiza el cumplimiento normativo sin esfuerzo manual.
  • Azure Monitor + Log Analytics:
    • Supervisión de pipelines (ej: fallos en Event Hubs) y alertas proactivas.
    • Justificación: Reduce tiempo de respuesta a incidentes.

Propuesta de Gobernanza del Dato y AI para Iberdrola: Alumbrado Público en Bizkaia

1. Introducción y Alcance

La gobernanza del dato y de la inteligencia artificial (AI) en este proyecto debe garantizar calidad, seguridad, cumplimiento normativo y sostenibilidad en el ciclo de vida de los datos y modelos, alineándose con los objetivos de Iberdrola: predicción de fallos, optimización energética y cumplimiento de NIS2/ISO 27001. Dada la madurez corporativa (Azure Data Lake, Databricks, Power BI) y las restricciones de presupuesto y equipo, la gobernanza se diseñará con un enfoque pragmático, escalable y centrado en el piloto (50K dispositivos).

El modelo de gobernanza propuesto se estructura en cuatro pilares:

  1. Gobernanza del dato: Calidad, seguridad, catalogación y cumplimiento.
  2. Gobernanza de AI: Ciclo de vida de modelos, explicabilidad y ética.
  3. Procesos y roles: Definición clara de responsabilidades y flujos de trabajo.
  4. Mecanismos de control: Monitoreo, auditoría y mejora continua.

2. Gobernanza del Dato

2.1. Políticas y Principios

Principios clave:

  • Calidad: Datos precisos, consistentes y actualizados para modelos confiables.
  • Seguridad: Protección de datos (incluyendo PII mínimo en SCADA) y cumplimiento de NIS2/ISO 27001.
  • Transparencia: Documentación clara de fuentes, transformaciones y usos de los datos.
  • Reutilización: Diseño del lakehouse para facilitar la integración con otros activos IoT (ej: contadores).

Políticas específicas:

  1. Calidad de datos:

    • Validación en origen: Reglas en Event Hubs/Databricks para descartar datos inválidos (ej: voltaje fuera de rango).
    • Limpieza automática: Uso de Spark en Databricks para corregir valores atípicos (ej: timestamps duplicados).
    • KPIs de calidad:
      • Completeness: >99% de datos sin gaps en ventanas de 15 minutos.
      • Consistency: Coherencia entre MQTT, SCADA y GIS (ej: misma geolocalización).
      • Timeliness: Datos procesados en <1 minuto para alertas críticas.

  2. Seguridad y cumplimiento:

    • Clasificación de datos:
      • Nivel 1 (Pública): Datos meteorológicos (AEMET), lecturas de voltaje sin PII.
      • Nivel 2 (Restringida): Datos de SCADA (pueden incluir PII mínimo, ej: IDs de dispositivos).
      • Nivel 3 (Confidencial): Datos de mantenimiento (si se integran en el futuro).
    • Acceso:
      • Azure AD + RBAC: Roles definidos en Purview (ej: Data_Ingestor, ML_Modeler, Compliance_Auditor).
      • Cifrado: En tránsito (TLS 1.2+) y en reposo (Azure Storage Service Encryption).
    • Auditoría:
      • Azure Purview: Registro de accesos a datos sensibles (SCADA) y cambios en esquemas.
      • Azure Monitor: Alertas para intentos de acceso no autorizados.

  3. Gestión del ciclo de vida:

    • Retención:
      • Datos brutos (ADLS): 5 años (requerido para auditorías NIS2).
      • Datos procesados (Delta Lake): 3 años (para retraining de modelos).
      • Modelos de ML: Versiones guardadas en MLflow/Azure ML por 2 años.
    • Eliminación:
      • Proceso manual en Purview para datos obsoletos (ej: dispositivos descomisionados).

Flujos de trabajo clave:

  1. Ingestión de datos:

    • Fuente → Event Hubs/ADF → Databricks (validación) → ADLS (zona bruta).
    • Dueño: Data Steward + Equipo de Datos.
    • Herramienta: Azure Purview para etiquetado automático (ej: "SCADA_Sensitive").

  2. Procesamiento y modelado:

    • ADLS → Databricks (feature engineering) → Azure ML (entrenamiento).
    • Dueño: ML Lead + Equipo de Datos.
    • Herramienta: MLflow para seguimiento de experimentos.

  3. Despliegue y monitoreo:

    • Modelo → API en Azure ML → Power BI/Azure Logic Apps (alertas).
    • Dueño: ML Lead + Equipo de Seguridad.
    • Herramienta: Azure Monitor para métricas de rendimiento (ej: latencia de API).

2.3. Mecanismos de Control

  1. Calidad de datos:

    • Automatizado:
      • Alertas en Databricks para datos con completeness <99%.
      • Validaciones en Event Hubs para formatos inválidos.
    • Manual:
      • Reuniones semanales con el Data Steward para revisar métricas de calidad.

  2. Seguridad:

    • Azure Policy:
      • Regla: "Todos los storage accounts deben tener cifrado en reposo".
      • Regla: "Acceso a SCADA solo para roles Data_Steward o Compliance_Officer".
    • Auditorías:
      • Purview genera informes mensuales de accesos a datos sensibles.

  3. Cumplimiento normativo:

    • NIS2:
      • Documentación en Purview de todos los activos críticos (ej: Event Hubs, SCADA).
      • Plan de respuesta a incidentes (ej: caída de Event Hubs) definido en Azure Sentinel.
    • ISO 27001:
      • Proceso de gestión de riesgos en Azure Policy (ej: bloquear puertos no autorizados).

3. Gobernanza de AI

3.1. Políticas para Modelos de ML

Principios:

  • Transparencia: Documentar inputs, lógica y limitaciones de cada modelo.
  • Explicabilidad: Usar técnicas como SHAP o LIME para modelos críticos (ej: predicción de fallos).
  • Ética: Evitar sesgos (ej: no discriminar por ubicación geográfica en optimización energética).
  • Sostenibilidad: Modelos eficientes (ej: XGBoost en lugar de deep learning) para cumplir el presupuesto.

Políticas específicas:

  1. Desarrollo de modelos:

    • Entrenamiento:
      • Datos de entrenamiento validados por el Data Steward (ej: sin leaks de tiempo en series temporales).
      • Uso de Azure ML Pipelines para automatizar retraining (ej: semanal).
    • Validación:
      • Métricas mínimas:
        • Predicción de fallos: AUC-ROC > 0.85.
        • Optimización energética: Error absoluto <10% en validación cruzada.
      • Pruebas de estrés: Simular fallos en datos para evaluar robustez.

  2. Despliegue y monitoreo:

    • APIs en Azure ML:
      • Autenticación con Azure AD.
      • Métricas monitoreadas: Latencia (<500ms), disponibilidad (>99.9%).
    • Feedback loop:
      • Alertas de fallos predichos → Equipo de Mantenimiento → Datos de reparaciones → Retraining.
      • Herramienta: Azure Logic Apps para orquestar este flujo.

  3. Retraining y actualización:

    • Frecuencia:
      • Modelos de predicción: Cada semana (con datos nuevos de MQTT/SCADA).
      • Modelos de optimización: Cada mes (para capturar tendencias estacionales).
    • Proceso:
      • Nuevo dataset → Validación por Data Steward → Entrenamiento en Azure ML → Pruebas A/B → Despliegue.

3.2. Explicabilidad y Ética

  • Técnicas:
    • SHAP/LIME: Para modelos de predicción de fallos (ej: "¿Qué variables contribuyen a un fallo?").
    • Azure ML Interpretability: Dashboard integrado para stakeholders.
  • Documentación:
    • Model Cards: Para cada modelo, con:
      • Objetivo, métricas, limitaciones (ej: "Modelo no válido para luminarias con <1 año de antigüedad").
      • Ejemplo de predicción con explicación (ej: "Falló por voltaje bajo + temperatura alta").
  • Ética:
    • Revisión por el equipo de seguridad para evitar sesgos (ej: no penalizar barrios con menos recursos).

    • Dashboard estratégico: Resaltar KPIs en tarjetas grandes y usar mapas para contexto geográfico.

    • Operativo: Filtros rápidos para priorizar luminarias (ej: "Solo riesgo alto").

    • Operativo: Notificaciones push para fallos críticos (ej: "Luminaria LUM123: voltaje crítico").
    • Táctico: Alertas si la precisión del modelo cae (ej: "Precisión del modelo: 78% (umbral: 80%)").

  5. Accesibilidad y movilidad:

    • Power BI Mobile: Para que los equipos de mantenimiento accedan desde el campo.
    • Tamaños de pantalla: Diseño responsive para pantallas grandes (ej: sala de control) y móviles.

02 Ingesta de Datos

Estrategia y pipelines con Azure Data Factory

Estrategia de Ingesta de Datos para el Proyecto de Optimización del Alumbrado Público en Bizkaia

1. Patrón de Ingesta por Fuente o Grupo de Fuentes

  • MQTT (2000 concentradores): Streaming. Debido a la naturaleza en tiempo real de los datos de telemetría, la ingesta debe ser continua para capturar todos los eventos y cambios en el estado de los dispositivos.
  • SCADA: Batch. Los datos históricos de operaciones, fallos y mantenimiento se pueden ingestar en lotes periódicos, como diario o semanal, dependiendo de la frecuencia de actualización de los registros.
  • SAP: Batch. Similar a SCADA, los datos financieros, de inventario y de recursos humanos se pueden ingestar en lotes, ajustando la frecuencia según la necesidad de actualización.
  • GIS (Azure Maps): Batch. Las ubicaciones geográficas y los datos de infraestructura se actualizan periódicamente, por lo que la ingesta puede ser por lotes, sincronizando con las actualizaciones de Azure Maps.
  • AEMET (Datos Meteorológicos): Streaming o Batch, dependiendo del servicio utilizado. Si se utiliza un servicio de datos en tiempo real, la ingesta debe ser streaming. De lo contrario, para servicios que proporcionan datos históricos o actualizaciones periódicas, la ingesta puede ser por lotes.

2. Estructura de Pipelines Recomendada

  • Pipeline de Ingesta de MQTT: Un pipeline dedicado para la ingesta en streaming de datos de telemetría, utilizando un conector de Azure Event Hubs para capturar los eventos en tiempo real. Este pipeline debe incluir una capa de procesamiento para limpiar y transformar los datos antes de almacenarlos.
  • Pipeline de Ingesta de SCADA y SAP: Un pipeline combinado para la ingesta por lotes de datos de SCADA y SAP, utilizando conectores específicos para cada sistema (como Azure Data Factory para SCADA y un conector SAP específico). Este pipeline debe incluir validaciones de datos y transformaciones para asegurar la consistencia y calidad de los datos.
  • Pipeline de Ingesta de GIS: Un pipeline para la ingesta por lotes de datos geográficos de Azure Maps, utilizando el conector de Azure Data Factory para Azure Maps. Este pipeline debe incluir la geocodificación de direcciones y la integración de datos geoespaciales.
  • Pipeline de Ingesta de AEMET: Un pipeline para la ingesta de datos meteorológicos, ya sea en streaming o por lotes, dependiendo del servicio de AEMET utilizado. Este pipeline debe incluir la transformación de datos meteorológicos para su integración con otros conjuntos de datos.

3. Conectores y Configuraciones Clave

  • Azure Event Hubs para MQTT: Configurado para capturar eventos en tiempo real con una frecuencia de procesamiento ajustada para manejar el volumen de datos.
  • Conectores de Azure Data Factory para SCADA y SAP: Configurados para la ingesta por lotes, con programaciones ajustadas según la frecuencia de actualización de los sistemas.
  • Conector de Azure Data Factory para Azure Maps: Configurado para la ingesta por lotes de datos geográficos, sincronizando con las actualizaciones de Azure Maps.
  • API o Conector de AEMET: Configurado según el servicio utilizado, ya sea para ingesta en streaming o por lotes, asegurando la autenticación y autorización adecuadas.

4. Cadencias y Dependencias entre Pipelines

  • Cadencia de Ingesta de MQTT: Continua, en tiempo real.
  • Cadencia de Ingesta de SCADA y SAP: Diaria o semanal, dependiendo de la frecuencia de actualización de los sistemas.
  • Cadencia de Ingesta de GIS: Periódica, ajustada a las actualizaciones de Azure Maps.
  • Cadencia de Ingesta de AEMET: Dependiendo del servicio, puede ser en tiempo real o periódica.
  • Dependencias: La ingesta de datos de SCADA y SAP puede depender de la disponibilidad de los sistemas y la calidad de los datos. La ingesta de datos de GIS y AEMET puede depender de las actualizaciones de los servicios y la disponibilidad de los datos.

5. Riesgos Identificados y Recomendaciones de Mitigación

  • Riesgo de Calidad de Datos: Implementar validaciones y limpieza de datos en cada pipeline para asegurar la calidad de los datos ingestados.
  • Riesgo de Acceso a Sistemas: Establecer acuerdos formales con los propietarios de los sistemas para garantizar el acceso a los datos.
  • Riesgo de Seguridad: Implementar protocolos de seguridad adecuados para proteger los datos, especialmente los datos en tiempo real y los sistemas de control.
  • Riesgo de Dependencia Tecnológica: Evaluar y comparar diferentes tecnologías y herramientas para asegurarse de la mejor elección para el proyecto, considerando la escalabilidad y el soporte.

Al implementar esta estrategia de ingesta de datos, es crucial monitorear continuamente el rendimiento de los pipelines, la calidad de los datos y los posibles riesgos identificados, ajustando la estrategia según sea necesario para asegurar la integridad y el valor de los datos para el proyecto de optimización del alumbrado público en Bizkaia.

04 Procesamiento ETL

Transformación, calidad de datos y orquestación
Databricks · Synapse

1. Decisión y justificación del motor de procesamiento

Basándonos en el análisis previo, consideramos que el perfil del cliente requiere un motor distribuido como Spark, específicamente Databricks, debido al volumen de datos y la complejidad de las transformaciones necesarias. Aunque el cliente tiene experiencia en SQL, la cantidad de datos (20 GB/día y 20 TB de histórico) y la necesidad de procesar datos en tiempo real desde los dispositivos telemétricos (MQTT) justifican la elección de Databricks. Además, Databricks ofrece una plataforma unificada para ingenieros de datos y científicos de datos, lo que facilita la colaboración y el desarrollo de modelos de machine learning.

2. Transformaciones principales por capa

Las transformaciones principales se llevarán a cabo en las siguientes capas:

  • Bronze (Raw) → Silver (Processed): En esta capa, se realizarán las siguientes transformaciones:
    • Limpieza y validación de datos: se eliminarán los datos duplicados, se corregirán errores de formato y se validarán los datos contra esquemas predefinidos.
    • Transformación de datos: se convertirán los datos de formato JSON a Parquet para mejorar el rendimiento de las consultas.
    • Agrupación y agregación de datos: se agruparán los datos por dispositivo y se calcularán agregados como la media y la desviación estándar de los valores de voltaje y consumo.
  • Silver (Processed) → Gold (Transformed): En esta capa, se realizarán las siguientes transformaciones:
    • Creación de características: se crearán características adicionales como la relación entre el voltaje y el consumo, y la tasa de cambio de estos valores.
    • Selección de características: se seleccionarán las características más relevantes para el modelo de predicción de fallos.
    • Preparación de datos para el modelo: se prepararán los datos para ser utilizados en el modelo de predicción de fallos, incluyendo la creación de conjuntos de entrenamiento y prueba.

3. Estrategia de calidad de datos y validaciones

La estrategia de calidad de datos se centrará en las siguientes áreas:

  • Validación de datos: se validarán los datos en cada capa para asegurarse de que cumplan con los esquemas y formatos esperados.
  • Detección de anomalías: se utilizarán técnicas de detección de anomalías para identificar datos que se desvían significativamente de los patrones esperados.
  • Reconciliación de datos: se reconciliarán los datos entre las diferentes fuentes para asegurarse de que sean consistentes y precisos.

4. Orquestación y scheduling de jobs

La orquestación y el scheduling de jobs se realizarán utilizando Apache Airflow, que se integrará con Databricks para ejecutar los jobs de procesamiento de datos. Los jobs se programarán para ejecutarse periódicamente, según la frecuencia de actualización de los datos.

5. Riesgos operativos y recomendaciones de mantenimiento

Los riesgos operativos incluyen:

  • Falta de calidad de datos: si los datos no son precisos o completos, los modelos de predicción de fallos no serán efectivos.
  • Problemas de escalabilidad: si el volumen de datos crece significativamente, el sistema puede no ser capaz de manejar la carga.
  • Falta de mantenimiento: si el sistema no se mantiene adecuadamente, puede dejar de funcionar correctamente.

Para mitigar estos riesgos, se recomienda:

  • Monitorear la calidad de datos: se deben monitorear constantemente los datos para asegurarse de que sean precisos y completos.
  • Escalabilidad: se debe diseñar el sistema para que sea escalable y pueda manejar crecimientos significativos en el volumen de datos.
  • Mantenimiento regular: se debe realizar un mantenimiento regular del sistema para asegurarse de que siga funcionando correctamente.

Modelo analítico, métricas y exposición de datos
Analysis Services · Gold

1. Decisión sobre el tipo de modelo analítico y justificación

Modelo recomendado: Esquema en estrella (star‑schema) sobre la capa Gold del lakehouse, complementado con una capa semántica en Power BI (Dataflows + modelo tabular) que sirva de punto único de acceso tanto a usuarios de negocio como a consumidores programáticos (APIs, notebooks ML).

Por qué esta elección:

Necesidad del cliente Implicación para el modelado Razón del star‑schema + capa semántica
Volumen 20 GB/día (≈ 20 TB histórico) Necesidad de consultas altamente optimizadas. El star‑schema permite pre‑agregar hechos y usar claves simples (surrogate keys). El motor de consulta de Synapse Serverless / Dedicated SQL sobre Delta aprovecha particiones y Z‑ordering sin penalizar la simplicidad del modelo.
Datos provenientes de 5 fuentes (MQTT, SCADA, SAP, GIS, AEMET) Necesidad de integrar fuentes heterogéneas y mantener trazabilidad. Las dimensiones aisladas (Device, Location, Time, Weather, Asset) centralizan atributos maestros y facilitan la gobernanza (Purview) y la reutilización en varios casos de uso.
Casos de uso mixtos (BI operativo, analítica avanzada, ML) Necesidad de una única “fuente de verdad” que sirva a todos los consumidores. La capa Gold mantiene los datos en Delta (ACID, versionado). El modelo semántico expone esas tablas como vistas lógicas; Power BI los consume directamente y los notebooks/servicios de ML pueden leerlas vía Spark SQL o Synapse.
Equipos con conocimientos SQL y Spark Necesidad de que tanto ingenieros de datos como analistas de negocio trabajen sobre el mismo modelo. El star‑schema es familiar para usuarios de SQL; la capa semántica oculta la complejidad física y permite a los analistas crear métricas en lenguaje DAX sin tocar Spark.
Requerimientos de latencia (casi tiempo real) Necesidad de datos actualizados cada 15 min. Los hechos se cargan en micro‑batches (Databricks Structured Streaming → Delta) y la capa semántica se refresca mediante incremental refresh de Power BI (máximo 15 min).
Cumplimiento NIS2 / ISO 27001 / ENS Necesidad de trazabilidad, control de acceso y auditoría. Delta + Purview + Azure RBAC proporcionan lineage y políticas de seguridad a nivel de tabla/columna. El modelo semántico hereda esas políticas cuando se publica como dataset Power BI.

En resumen, el star‑schema ofrece claridad de negocio (hechos‑dimensiones), rendimiento (agregados pre‑calculados, particionado) y flexibilidad (puede ser consumido por Power BI, APIs o ML sin transformación adicional). La capa semántica garantiza que la usabilidad sea la prioridad: los usuarios ven “Fact‑DeviceTelemetry”, “Dim‑Location”, etc., sin preocuparse por la arquitectura subyacente.

06 Machine Learning & MLOps

Modelos de IA, ciclo de vida y monitorización
Azure Machine Learning

1. Casos de uso de ML priorizados y tipo de modelo recomendado

  • Predicción de fallos de luminarias (clasificación binaria)

    • Modelo recomendado: XGBoost o LightGBM con técnicas de ensamblado (stacking) para capturar relaciones no lineales entre voltaje, consumo, estado de la luminaria y variables climáticas.
    • Justificación: Los modelos de boosting ofrecen alta precisión con un coste computacional moderado, se integran fácilmente en Databricks y en Azure ML, y permiten la interpretación de importancia de características (SHAP) que facilita la adopción por parte de los equipos de mantenimiento.

  • Forecast energético de lámparas (forecasting de series temporales)

    • Modelo recomendado: Prophet para patrones estacionales y de tendencia sencillos; si el patrón se vuelve más complejo, se migrará a un LSTM‑CNN híbrido entrenado en Databricks.
    • Justificación: Prophet es rápido de entrenar, requiere poca ingeniería de features y se adapta bien a la frecuencia de 15 min. La forma de “caja negra” del LSTM será considerada solo cuando la métrica de error de Prophet supere el 10 % de la variabilidad histórica.

  • Detección de anomalías en tiempo real

    • Modelo recomendado: Isolation Forest o Autoencoder (si la arquitectura de datos lo permite) ejecutado como micro‑batch cada 5 min.
    • Justificación: Los algoritmos basados en distancia no requieren etiquetado y pueden detectar patrones atípicos en la distribución de voltaje/consumo antes de que se conviertan en fallos.

  • Control dinámico de iluminación (futuro)

    • Modelo recomendado: Reinforcement Learning (RL) con un entorno simulado que combine la demanda de luz, el consumo energético y las restricciones normativas.
    • Justificación: Esta fase se reserva para la segunda fase de madurez cuando se cuente con datos históricos de consumo por zona y un modelo de predicción confiable. El RL permitirá optimizar la activación de luminarias en tiempo real, reduciendo el consumo en un 15 % de forma sostenible.

4. Ciclo de vida del modelo

  1. Recolección & Feature Engineering

    • Ingesta de datos en tiempo real (MQTT) y batch (SCADA, SAP, GIS, AEMET).
    • Transformaciones en la capa Silver (limpieza, enriquecimiento, generación de features como “tasa de cambio de voltaje”, “media móvil de consumo”).
    • Persistencia en Delta Lake (Gold) con particionado por fecha y dispositivo.

  2. Entrenamiento

    • Se crea un notebook de Databricks que lee el dataset Gold, aplica la selección de features y entrena el modelo XGBoost/LightGBM.
    • Se ejecuta un Experiment en MLflow; se guardan métricas de validación (AUC‑ROC, precisión, recall) y el artefacto del modelo.
    • Se realiza un cross‑validation temporal (time‑series split) para asegurar la robustez frente al drift.

  3. Validación & A/B Testing

    • El modelo se despliega en un staging endpoint de Azure ML.
    • Se compara la salida con el modelo histórico (baseline) usando métricas de negocio (tasa de detección de fallos reales).
    • Si la mejora supera el umbral (p. ej., 5 % de aumento en detección), se aprueba la migración a producción.

  4. Despliegue

    • Se publica el modelo en un Azure ML endpoint (real‑time) con autoscaling.
    • Se integra el endpoint en el pipeline de inferencia de Databricks (cada 15 min) que escribe los resultados en Fact_FailurePrediction.
    • Se exponen los datos de predicción a Power BI y a los sistemas de tickets vía Azure API Management.

  5. Monitorización

    • Model drift: se calcula la distribución de la variable objetivo y la del score cada día; se dispara una alerta si la desviación supera el 10 %.
    • Performance: latencia de inferencia y tasa de errores de endpoint.
    • Business: métricas de detección de fallos (recall) y ahorro energético en tiempo real.
    • Se alimenta un dashboard de MLOps en Power BI con KPI de salud del modelo.

  6. Retraining

    • Se programa un job de retraining cada 30 días (o cuando el drift sea detectado).
    • Se utiliza un Azure ML pipeline que vuelve a ejecutar los pasos de feature engineering y entrenamiento, registrando el nuevo artefacto en MLflow.
    • Se implementa un canary deployment: el nuevo modelo se prueba en un 5 % de la producción antes de reemplazar al modelo en producción.

    • Encuestas de feedback cada 3 meses para ajustar funcionalidades.
    • Reuniones de revisión mensuales con stakeholders para validar métricas.

  5. Preparar para la escalabilidad:

    • Diseñar dashboards modulares para añadir nuevos casos de uso (ej: control dinámico de iluminación).
