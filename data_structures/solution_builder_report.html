Arquitectura Propuesta para FarmaNorte: Plataforma de Datos Unificada con Lakehouse, ML y Visualización

Objetivo: Diseñar una arquitectura escalable, eficiente y alineada con los objetivos de negocio de FarmaNorte (reducción de roturas de stock, optimización de inventario y precisión en previsión de demanda), aprovechando su stack tecnológico actual (Azure, SAP, SQL Server, Salesforce) y su equipo interno de 22 personas. La solución debe cumplir con los requisitos de trazabilidad normativa, cumplimiento RGPD/ISO 27001, y un MVP en 3–4 meses con presupuesto ajustado (150–200 k€).

1. Arquitectura General y Justificación

La arquitectura propuesta sigue un enfoque Lakehouse con capas medallion (Bronce/Plata/Oro), integrado en Azure Synapse Analytics, para unificar datos heterogéneos (SAP, SQL Server, Salesforce) y habilitar análisis avanzados con Machine Learning (ML) y visualización en Power BI. Este diseño prioriza:

  • Escalabilidad futura (crecimiento de datos y usuarios).
  • Autonomía del equipo técnico (22 personas con experiencia en SQL y herramientas Azure).
  • Cumplimiento normativo (trazabilidad, RGPD, ISO 27001).
  • MVP rápido con enfoque en valor negocio inmediato (reducción de roturas de stock y optimización de inventario).

1.1. Principios de Diseño

  1. Diseñar para el futuro, pero empezar con lo esencial:
  • Capa Bronce: Integración cruda de datos sin transformar (SAP, SQL Server, Salesforce).
  • Capa Plata: Limpieza, estandarización y enriquecimiento (ej: conversión de unidades, cálculo de KPIs).
  • Capa Oro: Modelos dimensional y ML listos para consumo (Power BI, APIs).
  • Evitar sobreingeniería: En el MVP, se prioriza la capa Bronce/Plata básica y un modelo ML simplificado (XGBoost).
  1. Leverage del stack existente:
  • Azure Synapse Analytics como núcleo del lakehouse (integración nativa con SQL Server, soporte a Delta Lake, y familiaridad del equipo con SQL).
  • Azure Data Factory (ADF) para orquestación ETL/ELT (bajo costo y conectores nativos para SAP/Salesforce).
  • Power BI para visualización (licencia existente y experiencia del equipo).
  1. Gobernanza y cumplimiento desde el inicio:
  • Azure Purview (fase 2) y Azure Policy para trazabilidad y cumplimiento normativo.
  • Azure Key Vault para gestión de secretos (credenciales SAP/Salesforce).
  • Delta Lake para versióning de datos y auditoría (cumplimiento RGPD).
  1. Enfoque incremental en ML:
  • Modelo inicial: XGBoost para previsión de demanda por producto/almacén (precisión >75% en MVP).
  • Iteración: Ajuste de features y algoritmos con feedback de los dashboards de Power BI.

2. Componentes de la Arquitectura y Justificación Técnica

2.1. Capa de Ingestión (Bronce)

Objetivo: Extraer datos crudos de las fuentes heterogéneas (SAP, SQL Server, Salesforce) y almacenarlos en un formato eficiente para análisis.
Tecnologías:

  • Azure Data Factory (ADF): Orquestación de pipelines con conectores nativos para:
  • SAP Business One (OData): Extracción diaria de ventas, pedidos y clientes.
  • SQL Server (Linked Services): Integración en tiempo real (cada 6h) de datos de stock y movimientos de almacén.
  • Salesforce (REST API): Sincronización semanal de datos de CRM (clientes, promociones).
  • Azure Data Lake Storage (ADLS) con Delta Lake:
  • Formato: Parquet (columnar) para eficiencia en consultas.
  • Versióning: Soporte ACID y auditoría (cumplimiento normativo).
  • Particionamiento: Por fecha y fuente (ej: sap/ventas/2024-05-01.parquet).

Justificación:

  • ADF es la opción más económica y de bajo mantenimiento para el equipo interno, con conectores preconfigurados para SAP/Salesforce.
  • Delta Lake en ADLS permite:
  • Trazabilidad: Historial de cambios para auditorías (requisito normativo).
  • Escalabilidad: Soporte para crecimiento de datos (2 TB históricos + GB/día).
  • Compatibilidad: Integración nativa con Synapse Spark y Azure ML.

Supuestos:

  • Los datos de Salesforce se integran en fase 2 para reducir complejidad en el MVP.
  • La frecuencia de extracción de SQL Server (cada 6h) se ajusta según la criticidad de los datos de stock.

2.2. Capa de Procesamiento (Plata)

Objetivo: Limpieza, estandarización y enriquecimiento de datos para análisis.
Tecnologías:

  • Azure Synapse Spark Pools:
  • Limpieza: Eliminación de duplicados (ej: pedidos cancelados), manejo de valores nulos, y estandarización de unidades (ej: "cajas de paracetamol" → "unidades").
  • Transformaciones: Unión de datos de ventas (SAP) + stock (SQL Server) para calcular KPIs como "días de cobertura de stock".
  • Synapse SQL (Serverless):
  • Consultas SQL optimizadas para agregaciones (ej: ventas por producto/mes).
  • Creación de tablas intermedias (ej: ventasporproducto_mes).

Justificación:

  • Synapse Spark es la opción más económica para el equipo interno (evita costos adicionales de Databricks en fase 1).
  • Synapse SQL permite al equipo usar sus habilidades en SQL para consultas ad-hoc y optimización de modelos dimensional.
  • Enfoque en limpieza: La mayoría de los problemas de FarmaNorte (roturas de stock) se deben a datos sucios (unidades inconsistentes, duplicados), por lo que esta capa es crítica.

Ejemplo de transformaciones:
`python

PySpark (Synapse) para estandarizar unidades

from pyspark.sql.functions import col, when

dfstock = dfstock.withColumn(
"unidades",
when(col("unidad") == "caja", col("cantidad") * 10) # 1 caja = 10 unidades
.otherwise(col("cantidad"))
)
`

2.3. Capa de Curación (Oro)

Objetivo: Crear modelos analíticos listos para consumo (Power BI, ML).
Componentes:

  1. Modelo Dimensional (Star Schema):
  • Tabla de hechos: Demanda (ventas, stock, previsión).
  • Dimensiones: Producto, Cliente, Almacén, Fecha.
  • Tecnología: Azure SQL Database (para optimización de consultas en Power BI) o Synapse SQL (si se requiere escalabilidad futura).
  • Optimizaciones:
  • Particionamiento por fecha.
  • Índices en columnas de filtro (ej: productoid, almacenid).
  1. Modelo de Machine Learning (Previsión de Demanda):
  • Datos de entrenamiento: Ventas históricas (últimos 2 años), stock, promociones, estacionalidad.
  • Preprocesamiento:
  • Normalización de features (ej: ventas por unidad).
  • Manejo de valores nulos (imputación).
  • Algoritmo: XGBoost (regresión) por su precisión en datos con patrones no lineales (ej: estacionalidad en medicamentos).
  • Entrenamiento: Azure Machine Learning con pipelines automatizados (semanal).
  • Despliegue: Endpoint REST en Azure ML para consumo por Power BI o APIs internas.
  • Monitoreo: Alertas en Azure Monitor si la precisión cae <80% (drift de datos).

Justificación:

  • Modelo dimensional: Optimizado para Power BI (consultas rápidas y dashboards interactivos).
  • XGBoost: Supera a modelos lineales en datos con estacionalidad (ej: mayor demanda de medicamentos en invierno).
  • Azure ML: Cumple con ISO 27001 y permite gobernanza de modelos (lineaje, auditoría).

Supuestos:

  • El modelo inicial se entrena con datos históricos de ventas y stock (sin segmentación por cliente en MVP).
  • La precisión objetivo para el MVP es >75% (ajustable con más datos en fase 2).

2.4. Capa de Consumo

Objetivo: Habilitar la toma de decisiones con visualización y alertas.
Componentes:

  1. Power BI:
  • Dashboards clave:
  • Roturas de stock: Alertas en tiempo real con umbrales configurables.
  • Precisión del modelo ML: Comparativa entre demanda real vs. prevista.
  • Inventario inmovilizado: Por producto/almacén (identificar oportunidades de reducción).
  • Conectores: Directos a Synapse SQL o Azure SQL Database para consultas optimizadas.
  1. Azure Monitor + Log Analytics:
  • Alertas proactivas:
  • Fallos en pipelines ADF.
  • Desviaciones en precisión del modelo ML (>15% de error).
  • Rendimiento de consultas en Synapse (lento >5s).

Justificación:

  • Power BI ya es conocido por el equipo y tiene licencia, reduciendo costos de capacitación.
  • Alertas en tiempo real para roturas de stock son críticas para el negocio (objetivo: −30%).
  • Azure Monitor integra gobernanza y operación sin herramientas adicionales.

2.5. Gobernanza y Cumplimiento

Objetivo: Garantizar trazabilidad, seguridad y cumplimiento normativo.
Componentes:

  1. Azure Purview (Fase 2):
  • Catalogación automática de tablas y lineajes de datos (cumplimiento ISO 27001).
  • Clasificación de datos sensibles (ej: medicamentos sujetos a trazabilidad).
  1. Azure Policy:
  • Restricciones de seguridad:
  • Cifrado en reposo para datos en ADLS.
  • RBAC para acceso a Synapse/ML.
  1. Azure Key Vault:
  • Gestión de secretos (credenciales SAP/Salesforce, certificados).
  1. Documentación:
  • Azure DevOps: Lineaje de datos y procedimientos para el equipo interno.

Justificación:

  • Purview es la opción más económica para gobernanza en Azure (alternativas como Collibra superan el presupuesto).
  • Key Vault centraliza credenciales y evita hardcoding (riesgo de seguridad).
  • Documentación en DevOps facilita la operación futura por el equipo interno.

2.6. Integración con Fuentes Externas

Objetivo: Conectar datos heterogéneos (SAP, SQL Server, Salesforce) con mínima sobrecarga.
Estrategia:

  1. SAP Business One (OData):
  • ADF + Conector OData: Extracción diaria de ventas, pedidos y clientes.
  • Transformación en Plata: Limpieza de duplicados (ej: pedidos cancelados) y estandarización de códigos de producto.
  1. SQL Server (Almacén):
  • Linked Services en ADF: Integración en tiempo real (cada 6h) para datos críticos de stock.
  • Sin transformaciones en Bronce: Los datos se usan directamente en Plata para cálculos de cobertura.
  1. Salesforce (CRM):
  • ADF + REST API: Sincronización semanal de clientes y promociones.
  • Fase 2: Integración más profunda (ej: segmentación por cliente en el modelo ML).

Justificación:

  • ADF con conectores nativos evita desarrollo custom y reduce costos.
  • Priorización de SQL Server en el MVP por su criticidad (datos de stock en tiempo real).
  • Salesforce se integra en fase 2 para enfocar recursos en el impacto inmediato (roturas de stock).

Propuesta de Gobernanza del Dato y de Inteligencia Artificial para FarmaNorte

1. Introducción y Alcance

La gobernanza del dato y de inteligencia artificial (IA) en FarmaNorte debe garantizar la calidad, seguridad, trazabilidad y cumplimiento normativo de los datos a lo largo de su ciclo de vida, así como la sostenibilidad y escalabilidad de los modelos de IA implementados. Dada la naturaleza regulada del sector farmacéutico (trazabilidad de medicamentos, RGPD, ISO 27001) y los objetivos de negocio (reducción de roturas de stock, optimización de inventario), la gobernanza debe alinearse con los principios de autonomía del equipo interno, eficiencia operativa y valor inmediato.

Esta propuesta define un marco de gobernanza adaptado a la madurez actual de FarmaNorte (baja madurez analítica, equipo técnico interno de 22 personas) y a las restricciones del proyecto (presupuesto de 150–200 k€, MVP en 3–4 meses). Se estructura en cuatro pilares:

  1. Gobernanza del dato (calidad, seguridad, trazabilidad).
  2. Gobernanza de modelos de IA (lineaje, monitoreo, ética).
  3. Estructura organizativa (roles, responsabilidades, capacitación).
  4. Procesos y políticas (operativos, de cumplimiento y escalables).

2. Gobernanza del Dato

2.1. Principios Clave

  1. Calidad del dato:
  • Definición: Datos completos, consistentes, precisos y actualizados para garantizar la fiabilidad de los análisis y modelos.
  • Enfoque: Priorizar la limpieza en la capas Bronce y Plata (ej: eliminación de duplicados, estandarización de unidades, manejo de valores nulos).
  • Métricas:
  • Tasa de duplicados (<5% en Plata).
  • Porcentaje de valores nulos (<1% en Oro).
  • Precisión de datos de stock (>99% en tiempo real).
  1. Seguridad y privacidad:
  • RGPD: Anonimización de datos personales (ej: clientes en Salesforce) en capas Plata/Oro.
  • Trazabilidad farmacéutica: Lineaje completo de medicamentos desde Bronce hasta consumo (cumplimiento normativo).
  • Acceso controlado: RBAC en Azure (Azure AD) para limitar acceso a datos sensibles (ej: stock de medicamentos críticos).
  1. Trazabilidad y cumplimiento:
  • Lineaje de datos: Registrar el origen, transformaciones y consumo de cada conjunto de datos (ej: "ventasporproducto" → modelo ML).
  • Audit trail: Logs de cambios en Delta Lake (versióning) y Azure Monitor para pipelines ADF/Synapse.
  • Certificaciones: Preparación para ISO 27001 con Azure Policy y Key Vault.
  1. Escalabilidad y sostenibilidad:
  • Arquitectura Lakehouse: Capas Bronce/Plata/Oro para separar responsabilidades y facilitar la evolución.
  • Automatización: Pipelines ADF con triggers basados en eventos (ej: nueva venta en SAP) para reducir carga manual.
  • Documentación: Lineaje y procedimientos en Azure DevOps para operación futura.

2.3. Políticas y Procedimientos

2.3.1. Política de Calidad del Dato

  • Regla: Todos los datos en la capa Bronce deben pasar validaciones automáticas (ej: formato de fechas, rangos de valores) antes de llegar a Plata.
  • Ejemplo: Rechazar registros de ventas con fechas futuras o cantidades negativas.
  • Proceso:
  1. Bronce: ADF ejecuta validaciones básicas (ej: WHERE cantidad > 0).
  2. Plata: Synapse Spark aplica transformaciones correctivas (ej: imputación de valores nulos).
  3. Oro: Datos validados para consumo (Power BI, ML).

2.3.2. Política de Seguridad

  • Acceso:
  • RBAC en Azure: Roles definidos por función (ej: Data Engineer puede modificar Plata, Analista solo consulta Oro).
  • Datos sensibles: Solo accesibles para equipos autorizados (ej: stock de medicamentos críticos).
  • Cifrado:
  • Reposo: Azure Storage con cifrado por defecto (AES-256).
  • Transmisión: TLS 1.2+ para todas las conexiones (SAP, Salesforce, SQL Server).
  • Secretos:
  • Credenciales de SAP/Salesforce almacenadas en Azure Key Vault (nunca en código o configuraciones).

2.3.3. Política de Trazabilidad

  • Lineaje automático:
  • Delta Lake: Versióning de tablas para auditoría (ej: saber quién modificó ventas_2024-05).
  • Azure Purview (fase 2): Catalogación de tablas y relaciones (ej: "tabla stock depende de movimientos_almacen").
  • Documentación:
  • Azure DevOps: Wiki con procedimientos para cada capa (ej: "Cómo limpiar duplicados en Plata").
  • Metadatos: Etiquetado de tablas con propósito (ej: sensible=TRUE para datos de trazabilidad).

2.3.4. Política de Cumplimiento

  • RGPD:
  • Anonimización de datos personales en capas Plata/Oro (ej: IDs de clientes reemplazados por tokens).
  • Registro de actividades de tratamiento (logs en Azure Monitor).
  • Normativa sanitaria:
  • Trazabilidad de medicamentos desde Bronce hasta consumo (ej: lotes, fechas de caducidad).
  • Alertas automáticas para stock crítico (ej: medicamentos con fecha de caducidad próxima).

2.4. Mecanismos de Control

3. Gobernanza de Modelos de IA

3.1. Principios Clave

  1. Transparencia:
  • Lineaje completo: Registrar origen de datos, preprocesamiento, entrenamiento y despliegue del modelo.

  1. Ética y Cumplimiento:
  • Sesgos: Evitar sesgos en previsión (ej: no discriminar por región si no es relevante).
  • Explicabilidad: Usar modelos interpretables (XGBoost permite feature importance).
  1. Escalabilidad:
  • Reutilización: Diseñar modelos modulares (ej: mismo XGBoost para diferentes productos).

Análisis Crítico del Problema de Negocio y Madurez de Datos en FarmaNorte

FarmaNorte opera en un sector altamente regulado (distribución farmacéutica) con desafíos críticos en gestión de stock, ventas y logística, agravados por una madurez analítica baja (reporting manual en Excel semanal) y datos fragmentados en sistemas heterogéneos (SAP Business One, SQL Server, Salesforce). Los problemas declarados —roturas de stock y exceso de capital inmovilizado— son síntomas de una cadena de suministro ineficiente, donde la falta de visibilidad en tiempo real, previsión de demanda precisa y integración de datos impiden una toma de decisiones basada en insights accionables.

1.1. Diagnóstico de la Madurez Analítica

  • Baja madurez: FarmaNorte carece de un Data Warehouse (DWH) o herramientas de Business Intelligence (BI) estructuradas. El reporting actual se basa en Excel semanal, lo que introduce:
  • Retrasos en la toma de decisiones (datos desactualizados).
  • Errores manuales (copiado de datos entre sistemas, fórmulas inconsistentes).
  • Falta de trazabilidad (imposible auditar el origen de los datos o las transformaciones aplicadas).
  • Datos fragmentados: Las fuentes críticas (ventas en SAP, stock en SQL Server, CRM en Salesforce) operan en silos, sin integración ni sincronización. Esto genera:
  • Inconsistencias (ej: un producto puede mostrar stock disponible en SAP pero agotado en el almacén).
  • Duplicidad de esfuerzos (ej: analistas recreando informes en Excel que podrían automatizarse).
  • Falta de contexto (ej: no se correlacionan ventas con promociones o estacionalidad).

1.2. Impacto en los KPIs de Negocio

Los objetivos declarados por FarmaNorte —reducción del 30% en roturas de stock y optimización del inventario inmovilizado— están directamente ligados a tres problemas subyacentes:

  1. Falta de previsión de demanda:
  • Sin un modelo predictivo, FarmaNorte depende de estimaciones manuales (basadas en experiencia o datos históricos incompletos), lo que lleva a:
  • Sobrestock en productos con demanda impredecible (ej: medicamentos estacionales).
  • Faltantes en productos con alta rotación (ej: paracetamol en invierno).
  • Ejemplo: Un modelo de previsión con precisión >85% podría reducir el exceso de inventario en un 20–30% (según benchmarks del sector).
  1. Integración deficiente entre sistemas:
  • La falta de sincronización entre SAP (ventas), SQL Server (stock) y Salesforce (CRM) genera:
  • Roturas de stock no detectadas (ej: un pedido en SAP no se refleja en el inventario real).
  • Pedidos duplicados (ej: un cliente realiza un pedido en Salesforce y otro en SAP, pero el stock se actualiza solo en uno).
  • Ejemplo: Una integración en tiempo real entre SAP y SQL Server podría reducir roturas de stock en un 15–25%.
  1. Falta de visibilidad operativa:
  • Sin dashboards en tiempo real, los equipos de logística y ventas actúan con información obsoleta, lo que aumenta:
  • Tiempos de respuesta a alertas de stock crítico.
  • Costos de transporte por pedidos de emergencia (ej: fletes urgentes para reponer stock).

1.3. Oportunidades Identificadas

  1. Unificación de datos en un Lakehouse:
  • Centralizar datos en Azure Synapse Analytics (con capas Bronce/Plata/Oro) permitiría:
  • Consistencia: Una única fuente de verdad para ventas, stock y CRM.
  • Automatización: Eliminar el reporting manual en Excel.
  • Escalabilidad: Soporte para crecimiento futuro (ej: añadir IoT de almacenes).
  1. Modelos de ML para previsión de demanda:
  • Un modelo basado en XGBoost (o alternativas como Prophet) podría:
  • Reducir roturas de stock al anticipar picos de demanda (ej: medicamentos en temporada de gripe).
  • Optimizar inventario al ajustar pedidos a proveedores según la previsión.
  1. Visualización en Power BI:
  • Dashboards interactivos con alertas en tiempo real para:
  • Roturas de stock (ej: umbrales configurables por producto).
  • Precisión del modelo ML (comparativa demanda real vs. prevista).
  • Inventario inmovilizado (identificar productos con baja rotación).

1.4. Riesgos y Barreras

  1. Calidad de los datos:
  • Problema: Datos sucios en SAP/SQL Server (duplicados, unidades inconsistentes, valores nulos).
  • Impacto: Modelos de ML con baja precisión o dashboards con información errónea.
  • Solución: Implementar validaciones en Bronce (ADF) y limpieza en Plata (Synapse Spark).
  1. Resistencia al cambio:
  • Problema: El equipo está acostumbrado a Excel y puede resistirse a adoptar herramientas como Synapse o Power BI.
  • Impacto: Baja adopción de la nueva plataforma.
  • Solución: Talleres prácticos que demuestren el valor inmediato (ej: "este dashboard te ahorrará 10 horas semanales en reporting").
  1. Presupuesto limitado:
  • Problema: 150–200 k€ es un presupuesto ajustado para un proyecto de esta envergadura.
  • Impacto: Posible alcance reducido o uso de herramientas menos robustas.
  • Solución: Priorizar Azure Synapse (más económico que Databricks) y ADF (bajo costo de orquestación).

>
> Contexto:

>
> Acción Recomendada:
> *"1. Priorice el reabastecimiento de los productos críticos en Barcelona (lista adjunta).
> 2. Investigue la caída en la precisión del modelo: revise si hay nuevas promociones en Salesforce o cambios en la estacionalidad.
> 3. Considere ajustar los umbrales de stock para productos con alta variabilidad de demanda."*

Ejemplo 2: Dashboard Operativo (Alerta de Stock Crítico)
> Situación:
> "¡Alerta! El Producto X (Paracetamol 500mg) en el Almacén Madrid tiene solo 3 unidades en stock (umbral crítico: 10 unidades)."
>
> Contexto:
> "La demanda prevista para los próximos 2 días es de 50 unidades (vs. 30 unidades históricas). El modelo ML indica un aumento del 15% en la demanda, posiblemente debido a una promoción activa en la región."
>
> Acción Recomendada:
> *"1. Genere un pedido de emergencia de 40 unidades (botón 'Generar pedido').
> 2. Verifique en Salesforce si hay una promoción activa para este producto.
> 3. Ajuste manualmente la previsión si considera que el modelo está subestimando la demanda."*

02 Ingesta de Datos

Estrategia y pipelines con Azure Data Factory
Azure Data Factory

Estrategia de Ingesta de Datos para FarmaNorte con Azure Data Factory

1. Patrón de Ingesta por Fuente o Grupo de Fuentes

Para cada fuente identificada, se recomienda el siguiente patrón de ingesta:

  • SAP: Ingesta batch diaria, utilizando el conector de SAP de Azure Data Factory (ADF) para extraer datos de ventas e inventario. Esto se debe a que los datos de SAP son cruciales para la previsión de demanda y el análisis de ventas, y una ingesta diaria asegura que los datos estén actualizados sin sobrecargar el sistema.
  • SQL Server: Ingesta batch diaria, utilizando el conector de SQL Server de ADF para extraer datos de inventario y stock. La ingesta diaria es adecuada para mantener los datos de inventario actualizados y reflejar cambios en el stock de manera oportuna.
  • Salesforce: Ingesta batch semanal, utilizando el conector de Salesforce de ADF para extraer datos de interacciones con clientes y leads. La ingesta semanal es suficiente para analizar tendencias en el comportamiento de los clientes y la generación de leads, sin requerir una actualización diaria.
  • Azure Data Factory (ADF) y Azure Synapse Analytics: No requieren una ingesta adicional, ya que ADF se utiliza para la ingesta y transformación de datos, y Synapse Analytics almacena los datos integrados. Sin embargo, es crucial monitorear los logs y metadatos de ADF para asegurar el funcionamiento correcto de los pipelines.
  • Power BI: No requiere ingesta, ya que se utiliza para la visualización y análisis de los datos almacenados en Synapse Analytics. Los datos se actualizan en Power BI según se configuren los informes y dashboards para reflejar los cambios en los datos subyacentes.

2. Estructura de Pipelines Recomendada en ADF

Se recomienda la siguiente estructura de pipelines en ADF:

  1. Pipeline de Ingesta de SAP: Extrae datos de ventas e inventario de SAP y los carga en una capa de bronce en Azure Data Lake Storage (ADLS).
  2. Pipeline de Ingesta de SQL Server: Extrae datos de inventario y stock de SQL Server y los carga en la capa de bronce en ADLS.
  3. Pipeline de Ingesta de Salesforce: Extrae datos de interacciones con clientes y leads de Salesforce y los carga en la capa de bronce en ADLS.
  4. Pipeline de Transformación: Transforma los datos de la capa de bronce en una capa de plata en ADLS, aplicando limpieza, estandarización y enriquecimiento de datos.
  5. Pipeline de Carga en Synapse Analytics: Carga los datos transformados de la capa de plata en Synapse Analytics para su análisis y reporting.

3. Conectores y Configuraciones Clave

  • Conector de SAP: Configurar el conector de SAP en ADF para conectarse al sistema SAP de FarmaNorte, especificando las tablas y campos relevantes para la extracción de datos.
  • Conector de SQL Server: Configurar el conector de SQL Server en ADF para conectarse a la base de datos de SQL Server de FarmaNorte, especificando las tablas y campos relevantes para la extracción de datos.
  • Conector de Salesforce: Configurar el conector de Salesforce en ADF para conectarse a la plataforma de Salesforce de FarmaNorte, especificando los objetos y campos relevantes para la extracción de datos.
  • Configuración de ADLS: Configurar ADLS para almacenar los datos en capas de bronce, plata y oro, según sea necesario, y asegurar la seguridad y el acceso adecuados a los datos.

4. Cadencias y Dependencias entre Pipelines

  • Cadencia de Ejecución: Los pipelines de ingesta de SAP y SQL Server se ejecutarán diariamente, mientras que el pipeline de ingesta de Salesforce se ejecutará semanalmente.
  • Dependencias: El pipeline de transformación dependerá de la exitosa ejecución de los pipelines de ingesta. El pipeline de carga en Synapse Analytics dependerá de la exitosa ejecución del pipeline de transformación.

5. Riesgos Identificados y Recomendaciones de Mitigación

  • Riesgo de Calidad de Datos: Los datos de SAP, SQL Server y Salesforce pueden contener errores o inconsistencias. Mitigación: Implementar validaciones y limpieza de datos en los pipelines de ingesta y transformación.
  • Riesgo de Configuración de ADF: La configuración incorrecta de ADF puede provocar fallos en los pipelines. Mitigación: Realizar pruebas exhaustivas de los pipelines antes de su implementación en producción y documentar la configuración para futuras referencias.
  • Riesgo de Seguridad: El acceso no autorizado a los datos puede comprometer la seguridad. Mitigación: Implementar controles de acceso y seguridad en ADLS y Synapse Analytics, y asegurar que solo los usuarios autorizados tengan acceso a los datos y pipelines.

Al implementar esta estrategia de ingesta de datos, FarmaNorte podrá asegurar la calidad y la integridad de sus datos, mejorar la eficiencia de sus procesos de ingesta y análisis, y tomar decisiones informadas basadas en datos precisos y oportunos.

03 Almacenamiento

Arquitectura de Data Lake con capas medallion
ADLS Gen2 · Synapse

Arquitectura de Almacenamiento para el Data Lake de FarmaNorte

Enfoque: Lakehouse simplificado con capas Bronce/Plata (sin capa Oro explícita), optimizado para MVP y operabilidad

1. Decisión sobre la estructura de capas: Medallion simplificado (Bronce/Plata)

Justificación:

  • Volumen y complejidad de datos: El MVP se centra en SAP (ventas) y SQL Server (stock), con datos estructurados y volúmenes manejables (2 TB históricos + crecimiento incremental). Salesforce se incorpora en fase 2, lo que reduce la necesidad de una capa Oro compleja en esta etapa.
  • Equipo y madurez: El equipo tiene experiencia en SQL y Azure, pero no en ingeniería de datos avanzada (ej: Spark a gran escala o pipelines complejos). Una arquitectura Bronce/Plata es suficiente para:
  • Bronce: Almacenar datos crudos de fuentes con metadatos básicos (fechas, fuentes, checksums).
  • Plata: Aplicar transformaciones ligeras (limpieza, estandarización, KPIs básicos como "días de cobertura de inventario") usando Synapse SQL (familiar para el equipo) en lugar de Spark.
  • Objetivos de negocio: El foco está en reducción de roturas de stock y dashboards operativos, no en modelos analíticos avanzados. La capa Plata ya puede alimentar directamente a Power BI y modelos ML simples (XGBoost) sin necesidad de una capa Oro separada.
  • Coste y operabilidad: Evitar la sobreingeniería de una capa Oro reduce costes de almacenamiento, mantenimiento y formación. La capa Plata actúa como "Oro ligero" para consumo directo.

Excepción: Si en el futuro se requiere segmentación por cliente o modelos ML más complejos, se añadirá una capa Oro solo para esos casos, pero no como parte del MVP.

2. Servicios de Azure recomendados y justificación

| Servicio | Uso | Justificación |
|----------------------------|-------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------|
| Azure Data Lake Storage Gen2 (ADLS Gen2) | Almacenamiento de capas Bronce/Plata. | Hierarchical Namespace permite estructura de carpetas como en un sistema de archivos, ideal para Medallion. Delta Lake (soportado nativamente) garantiza versióning, ACID y trazabilidad. Coste eficiente para 2 TB iniciales + crecimiento. |
| Azure Synapse Analytics | Capa Plata (transformaciones) y consumo (SQL Serverless). | Integración nativa con ADLS Gen2 (sin ETL adicional). Synapse SQL permite transformaciones con T-SQL (familiar para el equipo) y escalabilidad automática. Spark Pools se usan solo si se requiere procesamiento avanzado (fase 2). |
| Azure Data Factory (ADF) | Orquestación de pipelines de ingesta y transformación. | Conectores nativos para SAP, SQL Server y Salesforce. Bajo coste para el volumen actual. Monitoring integrado con Azure Monitor. |
| Azure Key Vault | Gestión de secretos (credenciales SAP/Salesforce). | Cumplimiento de seguridad sin sobrecargar ADF con credenciales en claro. |
| Azure Purview (fase 2) | Gobernanza y lineaje de datos (si se escala). | En el MVP, se usa Azure Policy para RBAC básico y documentación manual en Azure DevOps. |
| Power BI | Consumo y visualización. | Licencias existentes y experiencia del equipo. DirectQuery sobre Synapse SQL para evitar duplicar datos. |
| Azure Machine Learning | Modelos ML (XGBoost). | Integración con Synapse para entrenamiento. Azure ML Pipelines para automatizar retraining. |

Alternativas descartadas:

  • Azure Databricks: No es necesario en el MVP (el equipo no tiene experiencia y Synapse SQL cubre las necesidades). Se evaluaría en fase 2 si se requieren transformaciones complejas.
  • Azure SQL Database: No se usa como capa de almacenamiento crudo, pero podría albergar tablas de referencia (ej: catálogo de productos) para optimizar consultas en Synapse.

│
└── raw_backup/ # Copias de seguridad de Bronce (retención 30 días)
`

Estrategia de particionado:

  • Bronce:
  • Particionamiento por fecha natural (year=, month=, day=) para cada fuente. Esto optimiza consultas en Synapse (ej: "ventas del Q1 2023") y permite eliminación eficiente de datos antiguos.
  • Formato Delta Lake para soportar operaciones ACID, versióning y compaction automática.
  • Plata:
  • Particionamiento por fecha y dimensión (ej: ventasporproducto_mes=2023-01). Esto acelera consultas en Power BI y evita escaneos completos.
  • Tablas optimizadas para Synapse SQL (ej: clustering por product_id y fecha).

Nombres de archivos:

  • Usar convenciones claras como fuentetipodatofecha.parquet (ej: sapventas_2023-01-01.parquet).
  • Incluir checksums (ej: _checksum) en metadatos para validar integridad.

4. Políticas de retención y tier de acceso

| Capa | Retención | Tier de Almacenamiento | Justificación |
|-----------|-----------------------------|-----------------------------------|------------------------------------------------------------------------------------------------------|
| Bronce | 1 año (ajustable a 6 meses) | Hot (Standard) | Datos crudos necesarios para auditoría y reprocesamiento. Coste aceptable para 2 TB. |
| Plata | 3 años | Cool (Standard Cool) | Datos transformados con bajo acceso frecuente. Reduce costes sin perder disponibilidad. |
| Logs | 90 días | Hot | Necesarios para debugging de pipelines. |
| Raw Backup | 30 días | Hot | Copias de seguridad para recuperación puntual. |

Estrategia de tiering:

  • ADLS Gen2 soporta automáticamente Hot/Cool/Archive por contenedor o prefijo de carpeta.
  • Reglas de lifecycle en ADLS para mover datos de Bronce a Cool después de 6 meses y a Archive después de 1 año (si se requiere).
  • Excepción: Datos de Plata/referencia críticos para modelos ML (ej: catálogo de productos) se mantienen en Hot para evitar latencia.

Políticas de eliminación:

  • Bronce: Eliminar datos más antiguos de 1 año solo si no hay dependencias (ej: reprocesamientos). Usar Delta Lake para marcar como "eliminados" en lugar de borrar físicamente.
  • Plata: Eliminar datos más antiguos de 3 años tras validar que no son usados por modelos ML.

5. Consideraciones de seguridad y gobierno de acceso

Principios:

  1. Mínimo privilegio: Acceso basado en roles (ej: solo Data Engineers pueden escribir en Bronce).
  2. Separación de responsabilidades: Equipos de negocio no acceden a Bronce.
  3. Trazabilidad: Todos los accesos y modificaciones son auditables.

Implementación:
| Recurso | Control de Acceso | Herramienta |
|---------------------------|---------------------------------------------------------------------------------------|------------------------------------------|
| ADLS Gen2 | - RBAC de Azure (ej: Storage Blob Data Contributor para Data Engineers). | Azure Portal / Azure Policy |
| | - Acceso basado en carpetas: Solo lectura para Plata/Oro, escritura para Bronce. | ACLs en ADLS |
| Synapse Workspace | - Roles SQL (dbdatareader, dbdatawriter) para equipos específicos. | Synapse SQL RBAC |
| ADF Pipelines | - Managed Identity para ejecutar pipelines (evitar credenciales en claro). | Azure Key Vault + Managed Identity |
| Power BI | - Roles de Power BI (ej: Viewer para analistas, Admin para Data Scientists). | Power BI Service |
| Azure ML | - Azure ML Compute con acceso restringido a Data Scientists. | Azure ML Workspace RBAC |

Cumplimiento normativo:

  • RGPD/ISO 27001:
  • Pseudonimización: En Plata, reemplazar IDs de clientes por tokens (ej: customerid → customertoken).
  • Registro de accesos: Usar Azure Monitor para auditar accesos a datos sensibles (ej: inventario de medicamentos).
  • Cifrado: Cifrado en reposo (activado por defecto en ADLS) y en tránsito (TLS 1.2+).
  • Documentación:
  • Lineaje de datos: Registrar en Azure DevOps el origen, transformaciones y consumo de cada tabla (ej: "ventasporproductomes" proviene de bronce/sap/ventas*.parquet).
  • Glosario de datos: Documentar en Azure Data Catalog (o Excel compartido en MVP) los campos clave (ej: stockdisponible, fechaultima_actualizacion).

6. Riesgos y recomendaciones operativas

Riesgos críticos y mitigación:

  1. Calidad de datos en Bronce:
  • Riesgo: Datos sucios en SAP/SQL Server (ej: valores nulos en precio_venta).
  • Mitigación:
  • Validaciones en ADF: Usar actividades como Data Flow con reglas de limpieza básica (ej: filtrar registros con fecha > hoy).
  • Checksums: Generar hashes en Bronce y compararlos en Plata para detectar corrupción.
  • Alertas: Configurar Azure Monitor para notificar fallos en pipelines o datos con anomalías (ej: stock_negativo).
  1. Desempeño en Synapse:
  • Riesgo: Consultas lentas en Power BI si no se optimizan las tablas en Plata.
  • Mitigación:
  • Particionamiento y clustering: Diseñar tablas en Plata con columnas de partición y clustering (ej: CLUSTERED BY (product_id, fecha)).
  • Materialized Views: Crear vistas en Synapse SQL para KPIs frecuentes (ej: diascoberturainventario).
  • Synapse Serverless: Usar SQL Serverless para consultas ad-hoc y evitar costes de provisionamiento.
  1. Dependencia de SAP/Salesforce:
  • Riesgo: Cambios en los esquemas de SAP o Salesforce rompen pipelines.
  • Mitigación:
  • Esquemas flexibles: Usar Delta Lake para manejar cambios en el esquema (ej: añadir un campo nuevo sin romper pipelines).
  • Documentación: Registrar en Azure DevOps los campos esperados de cada fuente (ej: "SAP: tabla Ventas requiere campos product_id, cantidad, fecha").
  1. Costes ocultos:
  • Riesgo: Uso excesivo de Synapse Spark o almacenamiento en Hot.
  • Mitigación:
  • Cotas en Synapse: Limitar el uso de Spark a pipelines críticos.
  • Monitoring de costes: Usar Azure Cost Management para alertar si el gasto supera el presupuesto (ej: 150–200 k€).
  • Tiering automático: Configurar reglas de lifecycle en ADLS para mover datos a Cool/Archive.
  1. Adopción por el equipo:
  • Riesgo: Resistencia al cambio por falta de formación.
  • Mitigación:
  • Talleres prácticos: Enfocados en:
  • Data Engineers: Cómo depurar pipelines ADF y consultar datos en ADLS.
  • Analistas: Cómo usar Power BI con datos en Synapse (ej: DirectQuery vs. importación).
  • Data Scientists: Cómo entrenar modelos ML con datos en Plata (ej: usar synapse_ml para XGBoost).
  • Comunicación: Mostrar ganancias rápidas (ej: "este dashboard reduce un 30% el tiempo de reporting").

Recomendaciones operativas clave:

  • Backups incrementales: Usar Delta Lake para versioning y restaurar versiones anteriores si hay errores en transformaciones.
  • Documentación como código: Almacenar el diseño de pipelines y esquemas en Azure DevOps (ej: archivos YAML para ADF, scripts SQL para Synapse).
  • Prototipo de gobernanza: Implementar Azure Policy para:
  • Bloquear eliminaciones en Plata/Oro sin aprobación.
  • Forzar etiquetas en recursos (ej: environment=prod, owner=team_x).
  • Plan de desastre:
  • Recuperación de Bronce: Copias diarias a raw_backup/ con retención de 30 días.
  • Recuperación de Plata: Scripts de regeneración desde Bronce (ej: rebuild_plata.sh).

7. Roadmap de evolución (fase 2)

Si el MVP tiene éxito, se escalará con:

  1. Integración de Salesforce: Añadir capa Bronce para datos de CRM y extender Plata con segmentación por cliente.
  2. Capa Oro explícita: Para modelos ML avanzados (ej: segmentación de clientes, recomendaciones).
  3. Azure Purview: Para gobernanza automatizada (lineaje, clasificación de datos).
  4. Synapse Spark: Si se requieren transformaciones complejas (ej: procesamiento de texto en notas de Salesforce).

Conclusión:
Esta arquitectura Bronce/Plata simplificada equilibra rigor técnico, costes y operabilidad para FarmaNorte. Prioriza:

  • Datos críticos (SAP/SQL Server) en el MVP.
  • Herramientas familiares (Synapse SQL, Power BI, ADF).
  • Automatización desde el inicio (validaciones, alertas, backups).
  • Escalabilidad controlada (Delta Lake, tiering, gobernanza básica).

El enfoque evita la sobreingeniería de una capa Oro inicial y permite iterar hacia una solución más robusta si el negocio lo requiere. La clave está en documentar cada decisión y capacitar al equipo para que pueda mantenerla sin depender de consultores externos.

04 Procesamiento ETL

Transformación, calidad de datos y orquestación
Databricks · Synapse

1. Decisión y justificación entre Databricks y Synapse (o combinación)

Basándonos en el análisis previo y considerando el perfil del cliente, decidimos utilizar Azure Synapse Analytics como la herramienta principal para la capa de procesamiento y ETL. Esta decisión se justifica por varias razones:

  • Familiaridad del equipo: El equipo de FarmaNorte ya tiene experiencia con herramientas de Azure y SQL, lo que facilita la curva de aprendizaje y la adopción de Synapse.
  • Volumen de datos: Aunque el volumen de datos es significativo, Synapse es capaz de manejarlo de manera efectiva, especialmente considerando la estrategia de particionamiento y el uso de Delta Lake para optimizar el almacenamiento y el acceso a los datos.
  • Complejidad de transformaciones: Las transformaciones requeridas, aunque importantes, no necesitan la complejidad y el poder de procesamiento de Databricks. Synapse puede manejar las limpiezas, estandarizaciones y enriquecimientos de datos necesarios para las capas Bronze, Silver y Gold.
  • Costo y presupuesto: Utilizar Synapse se alinea mejor con el presupuesto del proyecto, ya que no requiere la inversión adicional en infraestructura y recursos que Databricks podría necesitar para este tamaño de proyecto.

2. Transformaciones principales por capa (Bronze→Silver, Silver→Gold)

  • Capa Bronze: En esta capa, se realizarán las siguientes transformaciones:
  • Integración de datos crudos de SAP, SQL Server y Salesforce.
  • Validaciones básicas para asegurar la calidad de los datos (fechas válidas, valores positivos, etc.).
  • Almacenamiento en ADLS con Delta Lake para aprovechar su capacidad de versionado y trazabilidad.
  • Capa Silver: Aquí, se aplicarán transformaciones más complejas:
  • Limpieza y eliminación de duplicados.
  • Estandarización de unidades y formatos.
  • Cálculo de KPIs básicos y generación de datos intermedios para análisis.
  • Capa Gold: En esta capa final, se prepararán los datos para su consumo:
  • Creación de modelos dimensionales para análisis.
  • Entrenamiento y despliegue de modelos de Machine Learning para previsión de demanda.
  • Preparación de datos para visualización en Power BI.

3. Estrategia de calidad de datos y validaciones

La estrategia de calidad de datos se centrará en asegurar la precisión, completitud y consistencia de los datos a lo largo de todas las capas. Se implementarán validaciones en cada paso del proceso ETL, desde la ingesta hasta la preparación de datos para análisis. Esto incluye:

  • Validaciones en la capa Bronze: Verificación de formatos, rangos de valores y fechas válidas.
  • Detección de anomalías: Uso de estadísticas y técnicas de Machine Learning para identificar datos atípicos o inconsistentes.
  • Reconciliación de datos: Procesos para resolver discrepancias entre fuentes de datos diferentes.

4. Orquestación y scheduling de jobs

La orquestación de los jobs de procesamiento se realizará utilizando Azure Data Factory (ADF), que ofrece una integración nativa con Synapse y permite programar y monitorear los pipelines de datos de manera eficiente. Se configurarán triggers basados en eventos y programaciones periódicas para asegurar que los datos se procesen de manera oportuna y consistente.

5. Riesgos operativos y recomendaciones de mantenimiento

Para mitigar los riesgos operativos, se recomienda:

  • Monitorización constante: Utilizar Azure Monitor para supervisar el rendimiento de los pipelines y detectar cualquier fallo o anomalía.
  • Capacitación del equipo: Proporcionar talleres y capacitación continua para que el equipo de FarmaNorte pueda operar y mantener la solución de manera efectiva.
  • Documentación detallada: Mantener una documentación actualizada de los procesos, pipelines y configuraciones para facilitar el mantenimiento y la resolución de problemas.
  • Revisión y ajuste periódico: Programar revisiones periódicas de la solución para asegurarse de que sigue alineada con los objetivos de negocio y ajustarla según sea necesario para reflejar cambios en los requisitos o en el entorno de datos.

  • Rationale: Maximiza la usabilidad (analistas pueden navegar por dimensiones familiares), mantiene rendimiento (consultas push‑down a Synapse) y permite exposición múltiple (BI, APIs, notebooks ML).

2. Entidades principales del modelo (hechos y dimensiones)

2.1 Tabla de hechos – FactTransaccionStock

  • Grano: Nivel de movimiento de inventario por producto‑almacén‑fecha. Cada fila representa la variación neta (entrada, salida, ajuste) de un SKU en un día concreto.
  • Columnas clave:
  • StockKey (PK compuesta) – referencia a la tabla de dimensión Dim_Stock (almacén, lote, ubicación).
  • ProductKey (FK a Dim_Producto)
  • DateKey (FK a Dim_Tiempo)
  • TransactionTypeKey (FK a Dim_TipoTransaccion)
  • Quantity (signed – positivo para ingreso, negativo para salida)
  • CostAmount (costo asociado a la cantidad)
  • SourceSystem (SAP, SQL‑Server, etc.)
  • Particionamiento: por DateKey (mes) y por WarehouseID para permitir carga incremental y consultas paralelas.

3. Métricas de negocio clave y cálculos precalculados

| Métrica | Descripción | Tipo de cálculo | Lugar de cálculo (pre‑agregado) |
|---------|-------------|-----------------|-------------------------------|

6. Consideraciones de rendimiento y escalabilidad

  1. Particionamiento y distribución
  • FactTransaccionStock hash‑distributed por ProductKey + range‑partitioned por DateKey (mes).
  • Dimensiones replicated (pequeñas) para evitar joins costosos.
  • Vistas materializadas creadas con CREATE MATERIALIZED VIEW y REFRESH incremental (solo nuevas particiones).
  1. Compresión y formato
  • Almacén de datos en Delta Lake (Parquet) con ZSTD (nivel 3) para reducir I/O.
  • Tablas de hechos en Synapse columnstore para lecturas analíticas intensivas.
  1. Escalado de recursos
  • Synapse DWU ajustable: iniciar con DW1000c (aprox. 1 k DWU) y escalar verticalmente a DW4000c si la carga de consultas supera los 30 s.
  • Spark pools en Silver para limpiezas y transformaciones, dimensionados con auto‑scale (min 4, max 16).
  1. Optimización de consultas
  • Uso de statistics automáticas (CREATE STATISTICS en columnas de join y filtro).
  • Result set caching habilitado en Synapse para consultas repetitivas de dashboards.
  • Materialized view para los KPIs críticos (stock on‑hand, roturas) evita escaneos completos del hecho.
  1. Monitoreo y ajuste continuo
  • Azure Monitor + Log Analytics para capturar latencia de pipelines, uso de DWU y tiempos de ejecución de consultas.
  • Alertas configuradas para: <br> • Tiempo de carga > 30 min. <br> • Fallos en refresh de vistas materializadas. <br> • Drift de precisión del modelo ML.
  • Revisión mensual de partitioning (p.ej., crear particiones semanales si el crecimiento supera 500 M rows/mes).
  1. Plan de crecimiento
  • Si la carga de datos supera los 5 TB mensuales, migrar FactTransaccionStock a Synapse Serverless + Lakehouse y mantener solo los agregados críticos en Dedicated SQL.
  • Para consultas de “low‑latency” (API stock), usar Azure Cosmos DB (Core SQL API) replicado desde la tabla de stock on‑hand mediante Synapse Link; permite sub‑milisegundo de respuesta sin impactar el DW.

Conclusión

El diseño propuesto combina la familiaridad de un esquema estrella con la flexibilidad de una capa semántica que traduce la complejidad técnica a conceptos de negocio claros (producto, almacén, tiempo, tipo de transacción).

  • Entidades bien definidas permiten a los analistas crear rápidamente los dashboards de roturas de stock, cobertura de inventario y costo de inventario.
  • Métricas precalculadas y vistas materializadas garantizan que los informes sean responsivos (< 5 s) aun con volúmenes crecientes.
  • Actualizaciones diarias y near‑real‑time aseguran la información más

Azure Machine Learning

1. Casos de uso de ML priorizados y tipo de modelo recomendado

  • Pronóstico de demanda diaria por SKU‑almacén

El objetivo es anticipar las ventas de cada producto en cada centro logístico para reducir roturas de stock y optimizar los niveles de inventario.
Modelo recomendado: XGBoost (Gradient Boosting Machine) entrenado con columnas históricas (ventas diarias, promociones, fechas de fin de semana, eventos de stock) y características de producto/almacén. XGBoost combina alta precisión, buena interpretabilidad (feature importance) y bajo coste de entrenamiento, lo que permite ciclos de aprendizaje rápidos en el entorno de Synapse.
Justificación: No requiere series de tiempo puras y puede aprovechar la tabla de hechos ya consolidada en Gold. Además, la salida (p. ej. “forecastnext30d”) se integra directamente en la vista de forecast que Power BI consumirá.

  • Detección de anomalías en el flujo de stock

Se necesita identificar eventos atípicos (pérdidas, ajustes erróneos, movimientos bruscos) que pueden indicar problemas operativos o fraude.
Modelo recomendado: Isolation Forest (modelo de bosque aleatorio de aislamiento) o One‑Class SVM para datos tabulares. Se entrenan sobre el historial de transacciones en la capa Silver, con una ventana de 90 días para capturar patrones normales.
Justificación: Son modelos ligeros, no requieren etiquetas, y se integran fácilmente como un job de Azure ML Pipeline que emite alertas a Azure Monitor.

  • Clasificación de riesgo de rotura futura

Identificar productos que tienen mayor probabilidad de quedar fuera de stock en el siguiente mes.
Modelo recomendado: LightGBM (también un booster de árboles, pero más rápido) entrenado sobre las mismas variables que el pronóstico, añadiendo métricas históricas de stock‑out.
Justificación: La salida es una probabilidad que puede usarse como umbral en los dashboards para priorizar acciones de re‑pedido y mejora de la cadena de suministro.

5. Métricas de evaluación técnicas y de negocio

  • Técnicas
  • MAE (error absoluto medio) – indica cuánto se desvía la predicción en unidades de stock.
  • RMSE – penaliza grandes errores.
  • MAPE – porcentaje de error, facilita comparar con objetivos de negocio.
  • R² – explicación de varianza.
  • Feature importance – ayuda a validar que las variables son coherentes con dominio (p. ej. promociones, fin de semana).
  • De negocio
  • Reducción de roturas de stock (% de días sin stock).
  • Cobertura de inventario (días de cobertura) – objetivo > 30 días.
  • Coste de inventario – valor monetario de stock on‑hand; objetivo de reducción de 10‑15 %.
  • Tiempo de ciclo de pedido – mejora en lead‑time real tras re‑ordenes basados en forecast.
  • ROI de la solución – horas ahorradas por analistas y reducción de pérdidas por roturas.

  • Modelo Tabular que consume las vistas materializadas de Synapse (ej: vwStockOnHand, vw_Forecast).

  • Centraliza la lógica de medidas (ej: DaysCover, ServiceLevel) y jerarquías (ej: DimProducto por ClaseTerapéutica).
  • Permite DirectQuery para consultas operativas y Import Mode para dashboards analíticos.
  • Soporte para Row-Level Security (RLS) por región/almacén.
  • Configuración:
  • Particiones: FactTransaccionStock particionada por mes para refresh incremental.
  • Columnas calculadas: Métricas como IsStockOut (si Stock_OnHand <= 0).
  • Perspectivas: Separar vistas para usuarios operativos (ej: "Stock en tiempo real") vs. analíticos (ej: "Cobertura histórica").
  • Power BI Premium Dataset:
  • Modo "Composite": Combina DirectQuery (para tablas pequeñas como DimProducto) e Import Mode (para agregaciones como vwStock_OnHand).
  • Actualización:
  • Incremental: Solo las nuevas particiones de FactTransaccionStock (ej: último día).
  • Full refresh: Semanal para métricas de gestión (ej: vwValorInventario).

D. Rendimiento y escalabilidad

  • Optimizaciones clave:
  • Synapse:
  • Tablas de hechos en columnstore con particionamiento por DateKey y WarehouseID.
  • Índices en columnas de filtro (ej: ProductKey, WarehouseKey).
  • Power BI/AAS:
  • Aggregations para métricas de alto consumo (ej: SUM(Quantity) por ProductKey).
  • Query folding: Asegurar que las consultas se ejecuten en Synapse (no en Power BI).
  • Cache:
  • Power BI: Cache de dataset por 12 h para dashboards analíticos.
  • APIs: Cache en Redis con TTL de 5 min para consultas de stock crítico.
